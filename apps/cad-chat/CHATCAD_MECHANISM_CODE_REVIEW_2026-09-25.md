# ChatCAD Code Review：讓 AI 更理解機構設計

日期：2026-09-25。審查基準：目前工作樹，HEAD `1b2a9a9`，分支 `無塵電纜機制`。
補測更新：2026-09-26，已完成 Design 真實生成、完整精算、播放與參數重建，見第 8 節。
本次只新增 review 筆記，未修改實作、提示詞或教訓資料，未切換現有分支；後續實作應依 repo 規則從 `develop` 開分支。

## 結論與優先順序

ChatCAD 已具備不錯的基礎：規格澄清、標準件工具、參數化 CAD、草模播放、幾何驗證與教訓回饋。真正需要補強的是**把機構意圖變成機器可以檢查的設計條件，再把檢查結果送回 AI**。

建議先做五件事：

1. **優先補機構接點閉合驗證**：Design 實測精算通過，但 30° 時連桿孔與銷中心相差 4.69 mm（F7）。
2. 修正「無解草模仍成功」與「無效 MOTION 被當成 SKIP」，讓模型收到可修正的失敗；全 SKIP 不應顯示「全部通過」（F8）。
3. 清除過期教訓，調整提示詞：先確認功能、輸入／輸出、機架、關節與傳動，再畫外形。
4. 加入小型 `mechanismSpec` 與快速機構預檢，逐步銜接 Sketch／Design，不急著建通用裝配求解器。
5. 修正實測發現的 Sketch→Design 摘要丟失問題：帶入原始場景與已確認需求，不只帶名稱和角度。

只增加「你是資深機構工程師」或更多公式，不足以修復目前的驗證缺口。

## 1. 需要優先修正的 findings

### F1 · P1 · 無解連桿會被鉗到切點，仍可成功呈現

**位置：** [sketchEval.js:254](src/lib/sketch/sketchEval.js#L254)、[present.mjs:23](src/server/sketch/present.mjs#L23)。**狀態：已重現。**

`pin_on_line` 的判別式小於零時，程式用 `Math.max(0, ...)` 繼續計算，只在結果附上 `degenerate: true`。搜尋 `apps/cad-chat/src`，目前只有產生此旗標的位置，沒有消費它的檢查。`presentSketch` 執行 schema 驗證與 compile，卻不拒絕這種運動無解。

重現：讀取既有 `cylinder_tilt.json` fixture，僅在記憶體把 `pin_on_line.link.len` 改成 `1`，在 `theta=30°` 求值：

```json
{
  "schemaOk": true,
  "warnings": [],
  "pin": { "point": [131, 25, 54], "degenerate": true },
  "actualLinkLength": 5.626933041053576,
  "declaredLength": 1
}
```

影響：AI 可以得到「成功」，但連桿實際長度已違反自己宣告的尺寸；修正迴圈沒有被觸發。

建議：保留畫面防 NaN 的容錯與驗證判定之間的區別。預檢對負判別式超出數值容差的情況回傳 `KINEMATIC_UNREACHABLE`，包含 derived id、drive 值、宣告長度與閉合殘差。在寫檔／版本增加之前阻擋；AI 應修桿長、鉸點位置或行程。若修正會改動已確認的功能行程，需回到澄清，不能偷偷縮行程。

驗收：上述反例必須失敗且不新增版本；有效 fixture 保持通過；接近切點的小量浮點誤差用明確容差处理。

### F2 · P1 · MOTION 宣告錯誤被併入「未執行掃掠」，自修條件不會啟動

**位置：** [pipeline.mjs:593](src/server/cad/pipeline.mjs#L593)、[tools.mjs:240](src/server/agent/tools.mjs#L240)、[prompt.mjs:164](src/server/agent/prompt.mjs#L164)。**狀態：已重現結果映射，已確認控制流程。**

`designChecksFromMeta` 即使收到 `motionErrs`，仍回 `ok:true, skipped:true`；`runValidateDesign` 的 sidecar 快路徑固定回 `ok:true`。提示詞則只要求「非 skipped 且 fail」時自修。

本地輸入 `motionErrs:['unknown moving label']`，得到：

```json
{"id":"motion_sweep","ok":true,"skipped":true,
 "note":"設計模式:略過掃掠;MOTION 宣告無效,運動示意不可用: unknown moving label"}
```

這不是要求每次都跑昂貴碰撞檢查：**宣告已知錯誤**和**尚未做掃掠**是兩件事。目前 UI 與版本戳有區分未驗證狀態，不能把這個 finding 說成「所有版本都被錯標 verified」。問題在 agent 自修訊號被弱化。

建議拆成 `motion_declaration` 與 `motion_sweep`：前者有錯就非 skipped／fail，後者未跑仍為 skipped。同時修改 `validate.py --motion-only` fallback，避免兩條路徑不一致。靜態零件不必強制有 MOTION；對已確認需要運動的需求，缺宣告才算需求不完整。

驗收：無效 label／axis／couple 引用觸發修復；有效宣告不啟動完整 BRep 掃掠；靜態件仍能生成；`pipeline.design.test.js` 目前鎖定舊行為的斷言需同步調整。

### F3 · P1 · 啟用中的舊教訓否定現有旋轉能力

**位置：** [lessons.json:625](data/lessons.json#L625)、[lessons.mjs:526](src/server/lessons.mjs#L526)、[runner.mjs:97](src/server/agent/runner.mjs#L97)。**狀態：已確認資料，已重現 digest。**

`LS-3` 為 `active`，規則仍稱「MOTION v1（僅 linear）」並要求旋轉輸出改成靜態幾何。這與現有 Design prompt、motion parser 支援 `revolute` 衝突，也與 prompt 要求大型組合件一次提交完整產生器存在張力。

對 repo 的 `data/lessons.json` 呼叫 `buildDigest`，確認輸出包含 `[LS-3]`，共 617 字元。這證明該資料被載入時會進摘要；**未確認目前正在運行的應用實際使用哪份 lesson store**，因此不宣稱所有使用者都已被注入。

建議先退役／拆寫 LS-3，留下仍成立的模組化 builder 建議；增加能力版本與適用機構標籤，讓過期能力描述不能自動升格為長期規則。既有「衝突以上方 prompt 為準」可保留，但不是資料正確性的替代品。

驗收：目前能力版本的 digest 不再含「僅 linear」；旋轉、齒輪齒條案例不因 lesson 被降級成靜態模型。

### F4 · P2 · 連桿的自動伸縮會掩蓋剛體閉合錯誤

**位置：** [prompt.sketch.mjs:180](src/server/agent/prompt.sketch.mjs#L180)、[sketchEval.js:266](src/lib/sketch/sketchEval.js#L266)。**狀態：已確認，屬建模語義缺口。**

prompt 要求連接兩個相對運動點的構件使用 `actuator/coupler`「自動對準＋伸縮」。求值器的 `coupler` 長度就是當下兩錨點距離，沒有固定長度約束。

對氣缸伸縮這是合理的視覺表示；對剛性連桿，卻可能把不閉合的機構畫成伸縮桿。不是所有 coupler 都錯：若錨點由正確的閉式解產生，長度可以保持不變；缺的是驗證機制。

建議區分剛性連桿與伸縮致動器。剛性桿需 `nominalLength` 與長度殘差檢查；actuator 需最短／最長安裝距離與行程範圍。四連桿目前不支援圓交圓閉鏈時，應標示能力限制，不能把輸出搖桿直接指定轉角當成原機構已驗證。

驗收：兩錨點距離隨時間改變的剛性桿必須報錯；伸縮致動器在允許範圍內通過。

### F5 · P2 · 假設確認仍缺跨回合的結構化閘門

**位置：** [tools.shared.mjs:39](src/server/agent/tools.shared.mjs#L39)、[tools.shared.mjs:64](src/server/agent/tools.shared.mjs#L64)、[runner.mjs:78](src/server/agent/runner.mjs#L78)。**狀態：已確認工具契約，未做 live agent 重現。**

`emit_spec` 會發 chips，但沒有在此處保存「哪個必要設計決策尚未確認」。做事閘門依賴 agent 已呼叫 `emit_clarify`；新回合開始就重設 `_clarifyPending=false`。

因此，若模型漏問，或使用者下一句只是在詢問選項差別，後端並沒有逐項確認狀態可供建模閘門使用。這是可能繞過產品流程的缺口，不表示模型每次都會搶跑。

建議保存需求欄位的 `source/status/revision`，區分 `unknown / assumed / confirmed / derived`。只有影響拓撲、功能或必要驗證的未決策項擋正式建模；顏色、裝飾等可以直接採預設。使用者明示「先做概念、採建議值」時，記錄允許的假設範圍，避免新增一套反覆確認流程。

## 2. 架構上仍需補齊的能力

### 2.1 同步動畫不是傳動約束

[cadMotion.js:62](src/lib/cadMotion.js#L62) 的 `couple` 共用主動軸的週期與進度，幅值仍來自各自的 travel／angle。正確比例可以由生成器填入，但播放器本身不證明齒數比、導程或齒條位移成立。

應把「物理傳動關係」與「動作時序」分開：齒輪比例是 relation；先夾緊、再翻轉、再鬆開是 sequence。不要讓兩者都只靠同步播放表達。

### 2.2 Sketch 與 Design 缺少可靠的語義交接

[prompt.sketch.mjs:232](src/server/agent/prompt.sketch.mjs#L232) 請使用者開新 Design 對話、貼入需求摘要；**介面實際已有「轉為正式設計」功能**，見 [App.jsx:1108](src/App.jsx#L1108)。因此問題不是缺少入口，而是交接內容過度簡化。

**F6 · P2 · 實際重現：** `promoteSketch` 只擷取 `bodies[].label` 和 `drives` 名稱／範圍，接著清空當前對話、切換模式，把人話摘要放入輸入框。沒有附上 scene 路徑、joint 配置、derived 連桿／氣缸、尺寸或原始確認規格。

本次摘要剩「機架、平台(輸出)、連桿銷」與「前傾角 θ 0~30°」，但要求下一個 agent「沿用其關節配置與行程」；新對話實際沒拿到足夠資料。氣缸與連桿是 derived，所以連名稱都被漏掉；氣缸只在標題中殘留，無法恢復位置和行程。詳見第 7.3 節的真實輸入框內容。

建議沿用現有按鈕，在後端建立含來源 session／version 的受限交接資料包，附原始 scene 與已確認需求；原檔缺失時明確告知摘要不完整。保留 body／joint id、尺寸、關節與支援程度，讓 Design 重新建幾何後比對語義，不必一開始就寫全自動 Sketch→CAD 編譯器。草模的 DOF≤2 是實作上限；不要把省略的軸誤當整台機器只有兩個自由度。

驗收：此案例轉 Design 後，仍取得 120 mm 連桿、35 mm 搖臂、氣缸固定軸線、平台樞軸、0～30° 輸出與約 17.59 mm 氣缸行程；不能只斷言輸入框有文字。

### 2.3 目前的正確性回饋偏幾何，缺少功能驗證

`cad_measure`／`cad_align`、完整精算與版本驗證戳值得保留。下一步需驗證「這個模型是否達成指定輸出」，例如目標行程、旋轉角、齒比、夾爪中心不漂移、工件交接不跳動。光看 STEP 生成成功或零件不相交，不能得出上述結論。

## 3. 提示詞建議：先建立設計摘要，再生成幾何

### 3.1 Design 的可直接試用草案

建議加入 `prompt.mjs` 的需求理解／規劃段，並整併重複規則。以下使用現有工具名稱，不假裝新增工具已存在：

```text
面對機構需求，先建立簡短、可核對的設計摘要，再生成 CAD：
1. 功能：輸入是什麼、希望哪個輸出件如何移動，以及動作順序。
2. 拓撲：固定機架、剛體、關節、主動輸入與被動從動件。
3. 幾何基準：單位、世界方向、關節軸與樞軸所在座標系。
4. 傳動：驅動源 → 傳動件 → 輸出件；必要比例、方向、行程及界限。
5. 工程條件：依任務所需辨識負載、速度、精度、空間、安裝與製造限制。
6. 驗收：把使用者的要求轉成幾項可量測的條件。

用 emit_spec 呈現關鍵需求與假設，用 emit_plan 簡述結構、傳動與驗收。
構型未定時比較 2–3 個可支援方案，說明適用條件與取捨，再用
emit_clarify 集中詢問會改變拓撲或功能的問題；遵守既有提問後停手閘門。
低影響外觀細節不必逐項提問。確認過的數值與使用者修正優先，勿重問。

不要把動畫驅動數當成機構自由度分析，不要把視覺接觸當成裝配約束。
couple 只提供同步進度，需另外讓 travel/angle 符合實際傳動關係。
剛性連桿不能為了保持連接而改變長度；能力不足時揭露簡化範圍。

cad_validate 的 skipped 代表未檢查，不是通過。
即使總 ok=true，note 若指出 MOTION 宣告無效，也應先修正再呈現。
最後簡述：完成的功能、實際已跑的驗證、未驗證項與保留假設。
```

最後一項是 F2 修正前的暫時補強；長期應依結構化檢查結果，避免解析人話 note。

### 3.2 Sketch 應改寫的關鍵段落

```text
草模優先表達正確拓撲、運動方向與功能關係。
actuator 是允許改變長度的致動器；coupler 若代表剛性桿，其兩端距離
必須在整個運動範圍保持設計桿長，不能用畫面自動伸縮掩蓋閉合錯誤。

閉式解無解、分支跳變或超出致動器範圍時，應修改設計或揭露不可行。
傳動角的讀數只適用於指定的受力與幾何定義，不是通用的機構合格證明。
```

需同步修改目前「自動伸縮，永不懸空」的原句，而非把互相矛盾的兩段都留著。這些文字不能取代 F1／F4 的程式檢查。

### 3.3 知識載入策略

保留短核心 prompt，把齒輪、連桿、螺桿、皮帶、夾爪與線纜等分成領域配方。每份配方應包含適用條件、不適用情境、必要輸入、支援等級、範例、失敗反例與驗收條件。

Design 可沿用 Read／Glob 的既有路徑；Sketch 目前只有 MCP 白名單、不能讀檔，應由伺服器依任務注入精簡配方或另加受限知識工具，不可只在 prompt 寫「請去讀 KB」。不要一次把所有領域文件塞進每回合。

## 4. 流程建議：最小可行的機構設計閉環

```text
需求 → 結構化設計摘要 → 必要澄清 → 拓撲與傳動方案
     → 快速機構預檢 → 草模／CAD 生成 → 功能比對與局部修正
     → 呈現已檢查範圍 → 精算／匯出
```

### 4.1 小型 mechanismSpec，不另做一套巨型 CAD 格式

建議新增以下資料；這是未實作的提案，不是現有 schema：

| 欄位 | 最小內容 | 用途 |
| --- | --- | --- |
| identity | schemaVersion、revision、來源版本 | 避免用舊規格驗新產物 |
| requirements | 值、單位、來源、確認狀態 | 保留使用者意圖與未決假設 |
| bodies / joints | 穩定 id、parent/child、型式、frame、axis、limits | 定義拓撲，對映生成器 labels |
| drives / relations | 主動輸入、被動輸出、公式型別、參數、方向 | 區分自由輸入與傳動關係 |
| sequence | 階段、前提、完成條件、工件狀態 | 描述取放、夾持、翻轉順序 |
| acceptance | 行程、角度、閉合殘差與容差 | 生成可執行驗收條件 |
| capability | 支援／簡化／未支援與原因 | 避免過度承諾 |

relation 初期只做少數具名型別，如 gear_pair、rack_pinion、lead_screw、rigid_link；使用確定性的 evaluator，不執行模型提供的任意公式字串。

### 4.2 預檢分三層，控制延遲

1. **每次必跑、低成本：** id 與單位、關節軸、標籤覆蓋、引用關係、宣告錯誤、必要需求欄位。
2. **機構相關才跑：** 起點、終點、階段交界、關鍵構形與有限採樣；检查閉合殘差、剛性桿長、傳動比例、輸出行程與交接連續性。靠近奇異點加密；可解析判定者優先用解析界限。有限採樣不得宣稱全域保證。
3. **按風險與匯出需求跑：** 完整幾何精算、運動掃掠。保留現有匯出閘，不必每個對話都完整重算。

先把第二層接進 `sketch_present` 的寫檔前路徑；Design 先完成 F2，再加必要功能檢查。相同版本的 spec／參數／產物應共用雜湊或版本識別，任何設計修改都使舊檢查失效。

### 4.3 工具要回傳工程診斷，而不只回成功／失敗

建議的新診斷格式，例如：

```json
{
  "ok": false,
  "stage": "kinematics",
```

### 8.3 F7 · P1 · 草模正確的閉鏈，進入 Design 後被降級且精算仍通過

**證據：** [生成器 MOTION:340](../../models/reviews/chatcad-20260925/design-v1/tilt_platform.py#L340)、[播放器矩陣](src/lib/cadMotionMath.js#L13)、[精算紀錄](../../models/reviews/chatcad-20260925/design-v1/full-validation.txt)。**狀態：真實產物已重現。**

生成器把平台與平台銷列入旋轉組，把 `link` 連桿列入缸桿的純平移組；主從共用正規化進度。AI 文字承認省略約 2.2° 的連桿擺動，也明講沒有掃連桿眼與銷，但又稱由 home 定位及 0.2 mm 孔隙「保證」。靜態孔隙不能補足運動後毫米級的接點分離。

用實際 `frameMatrix` 套用生成的 MOTION，追蹤初始皆在 `(100,100,35)` 的平台銷與連桿末端孔中心：

| 平台角度 | 接點中心偏差 mm | 宣告的缸桿位移 mm | 閉式解所需位移 mm |
| --- | ---: | ---: | ---: |
| 0° | 0 | 0 | 0 |
| 7.5° | 0.34457 | 4.39791 | 4.56879 |
| 15° | 1.22122 | 8.79583 | 9.06459 |
| 22.5° | 2.67173 | 13.19374 | 13.42350 |
| 30° | **4.69001** | 17.59165 | 17.59165 |

這不表示 STEP 的 home 幾何無效，也不表示碰撞器算錯；**缺少的是運動約束檢查，以及必要檢查配對的覆蓋檢查**。不碰撞和接頭仍閉合是不同的條件。此次草模定長閉合成功、Design 反而降級，是「兩套表示／驗證不共用」的具體反例。

建議：

- 將草模的閉式關係保留到 Design，至少支援此類 slider-crank 的具名 evaluator；播放器、掃掠與驗收使用同一份 pose 計算。
- 增加 joint anchor coincidence／rigid-link residual 檢查，讓 missing coverage 與超容差成為明確失敗。
- agent 不能只因 runtime 不支援就把關鍵運動改成近似並說「保證」。若必須降級，交付標成靜態／示意，列出未滿足要求；不要把碰撞通過當成功能完成。
- 驗收至少要求本例 0～30° 的桿長和兩端鉸點殘差在規定容差內，不能只核對 17.59 mm 終點行程。
