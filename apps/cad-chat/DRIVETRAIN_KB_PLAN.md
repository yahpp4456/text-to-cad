# 傳動構型選型知識庫(KB)+ 選型澄清流程 — 定稿計畫

> **2026-07-11 定稿**(初稿經逐條查證 + 「同一份做到底」框架再評估後修訂)。
> 目標:讓 cad-chat 的 AI 面對模糊機構需求時,懂得推薦真實傳動構型,且使用者選定後
> **建得出通過驗證的示意模型**——選型與建模兩段都在本次交付內成立。照 §9 執行。

---

## 1. 問題(Motivation)

使用者對 agent 說「我想設計機器手臂用的馬達減速機」,agent 只會畫**兩顆正齒輪的比例減速**——
因為它手上**零減速機構型知識**:諧波(harmonic drive)、行星(planetary)、擺線/RV、蝸輪蝸桿
這些真實工程選型,它都不知道該不該推薦。

探索後確認三件事(已逐條對照原始碼/檔案查證屬實):

- 本地既有機構知識庫(`ref/mechanism_engineering_suite`)**明文把諧波/行星列為「目錄外、
  禁止臨時臆造」**(`3b_mechanism_kb_project_entries.md`)——補不上這塊。
- cadpy.parts 的幾何能力只到**正齒輪 + 齒條**,沒有行星/內齒環/諧波/擺線的產生器。
- 但**幾何天花板夠高**:`benchmarks/10-planetary-gear-stage.md` 證明行星輪系(含內齒環)
  可用一次性 build123d 程式做出來(該 benchmark 用**梯形簡化齒、直接指定內齒三徑**,
  非漸開線),只是沒沉澱成可重用產生器。

所以 agent「只會兩顆齒輪」是必然的:它根本沒有構型層的知識可查。

**血統註記**:本方案的「KB 條目 + 路由索引 + 目錄外構型先補條目再動手」架構,沿用
`ref/mechanism_engineering_suite` 被驗證過的模式(`3b` + `router_activation_card` + `6_合成決策`),
等於用輕量方式補上 fork 當初刻意未做的「互動式合成⑤」(見 memory `mech-mcp-borrow`)。

## 2. 已裁決的方向(Decisions)

1. **完全不開 WebSearch / WebFetch**——agent 維持零網路。理由:訂閱 OAuth 是否支援
   WebSearch 官方文件未明說(有認證失敗風險)、每回合等搜尋拖慢、品質不穩;純本地方案
   回合最快、零認證風險。
2. 走**純本地知識庫(KB)**:把「傳動/減速構型選型」寫成 markdown 放進 repo,agent 用
   內建 Read 工具查(它的工作目錄就是 repo 根,Read/Glob/Grep 已在白名單內)。
3. **互動流程**:agent 遇到「構型未定」的需求 → 查 KB → 用**既有的澄清卡機制**給 2–3 個
   候選構型(附取捨與建議)→ 使用者選定 → **建幾何示意版**(並誠實說明簡化了什麼)。
4. **KB 附一份擴充規範**:讓使用者(懂規格的機構工程師、非程式人)之後能**自己新增領域/
   條目**——複製範本、補一行索引就生效,**完全不用改程式**。
5. **交付深度(再評估裁決)**:
   - **配方入庫鐵律**:KB 每種構型的「示意版建模要點」,寫進 KB 前**必先用一次性產生器
     實跑過 `check_geometry`**(交付期預驗,見 §7 第 0 層)。驗不過的當場改配方,
     不留給 runtime 燒 retry。
   - **本次不新增任何 `cadpy.parts` 產生器**;唯一例外是把**行星示意**在預驗產生器基礎上
     多走一步、留成 `models/planetary_reducer/` dogfood 參考模型(比照 `flip_gripper` /
     `steering_box_rack_pinion` 的角色,KB 行星節直接指向它)。理由:七構型全上產生器是
     過度投資;行星是唯一「有 benchmark 前例 + 減速需求最常中選」的構型,值得一個真模型
     錨點。其他構型的配方經預驗後以文字+程式片段住在 KB,等實際使用出現重複需求再升級
     ——與 repo 一貫「先 dogfood 再沉澱」路徑一致。

## 3. 這方案為什麼可行(既有機制,直接沿用;均已對碼查證)

- **澄清卡已經存在**:agent 呼叫 `emit_clarify(question, options, suggested)` 就會在畫面上
  跳出一張兩步精靈卡,使用者點選項後,選項的文字會原樣送回給 agent 當作回覆繼續。
  → 「給候選構型讓使用者選」**零 UI 改動**,直接用這張卡。
  選項是 `{label, value}` 結構(`tools.mjs` emit_clarify schema):`label` 是按鈕上給人看的
  短字、`value` 是點下去送回的完整內容。所以**取捨摘要放 label(給人看),選定後的完整
  配置放 value(給下一回合的 agent 接手)**。
- **「不搶跑」有程式硬閘門**:`emit_clarify` 之後同回合的一切 `cad_*` 工具會被
  `clarifyGate`(`session._clarifyPending`)直接拒絕——「先選型澄清、不得先建模」不是
  單靠 prompt 紀律,是程式強制。L4 要驗的只剩「agent 會不會根本不問就直接建」。
- **prompt 已有「特定構型先讀參考檔」的句式**(龍門類先讀 xyz_pickplace_gantry、齒輪齒條類
  先讀 steering_box_rack_pinion),新的 KB 指引沿用同一句式,風格一致;
  「驅動方式未定必列澄清選項」也有現成先例可仿寫(錨點 B 的範本)。
- **回合沒有 timeout / maxTurns**,agent 中途多讀一個 KB 檔不會撞到任何限制。
- **turn 2 的建模要點靠 SDK resume 傳遞**:turn 1 把領域檔**整檔** Read 進 transcript,
  使用者選定後的下一回合天然拿得到配方(所以錨點 A 必須寫「整檔讀」,見 §6)。

## 4. KB 目錄設計:`apps/cad-chat/kb/`(新目錄)

```
apps/cad-chat/kb/
  INDEX.md                  # 路由索引:一行一領域(檔名|一句用途|觸發關鍵詞)
  README.md                 # 擴充規範(使用者自行加領域的完整規則)
  _TEMPLATE.md              # 複製即用的領域檔空骨架(含全部必要標題 + 填寫提示)
  drivetrain-reduction.md   # 本次交付:減速機 / 旋轉傳動構型選型
```

**為什麼放這裡**:唯一的消費者是 cad-chat 的 agent。不放 `skills/`(規定 skill 必須自包含、
不得被外部引用)、不放 `packages/`(那是共用程式碼,且會被 sync-vendored 複製 8 份、白白拖
markdown)、不放 `models/`(那是 CAD 產物區;**例外**:行星 dogfood 是 CAD 模型,照規定
住 `models/planetary_reducer/`,KB 只放指向它的參考)、不動 `ref/mechanism_engineering_suite/`
(是一個 untracked 的獨立外部 git repo,只借它的架構靈感)。放在 fork 主軸 app 的子樹內,
未來 merge upstream 摩擦最小。

### 4.1 發現機制 = 一個索引檔(不是掃目錄)

prompt 裡**只寫死一個路徑**:`apps/cad-chat/kb/INDEX.md`(完整 repo 根相對路徑——agent 的
cwd 是 repo 根,不得用 `kb/` 簡寫)。agent 觸發時先讀這個索引,依觸發關鍵詞決定要讀哪個
領域檔。索引每行格式固定(給人也給測試解析):

```
- drivetrain-reduction.md|減速機/旋轉傳動構型選型|觸發:減速機、減速比、齒輪箱、機器手臂關節、諧波、行星、擺線、RV、蝸輪、同步帶
```

**為什麼用索引檔而不是讓 agent 掃檔名**:檔名承載的資訊太少,agent 會讀錯檔或漏配;
索引一行就把「這檔管什麼、什麼時候該讀」講清楚,token 成本固定在「一行 × 領域數」,
而且只在觸發時才讀。索引與實檔對不上(漂移)的風險,由下面的格式守護測試雙向鎖住。

**擴充體驗**:使用者加一個新領域 = 複製 `_TEMPLATE.md`、改名、填內容、在 INDEX 補一行 →
生效。**完全不碰任何 `.mjs`,也不用重啟 server**(KB 是即時 Read 進來的,不進 prompt)。

### 4.2 `README.md`(擴充規範,寫給非程式人)

涵蓋:①這目錄是什麼;②新增一個領域的步驟清單;③領域檔**必要的章節標題**(測試會驗,
缺了會紅);④數值標註慣例(只給典型範圍、行尾標`〔信心:高|中|低〕`、來源集中寫檔尾);
⑤「示意版建模要點」段的寫法(只能引用 repo 既有能力、每個構型必須誠實寫出「做不到的事」、
必須提醒建模契約的坑);⑥**配方預驗聲明**:新配方入庫前必須先用一次性產生器跑過
`check_geometry`,並在該構型節尾標「已預驗:YYYY-MM-DD」——格式測試不驗這條(驗不了),
是寫給擴充者的紀律條款。

### 4.3 領域檔必要章節(格式契約)

`# <領域名>`、`## 適用情境`、`## 選型速查表`、每個構型一節 `## 構型:<名稱>`(節內必含
`### 選型維度` 與 `### 示意版建模要點`)、檔尾 `## 資料信心與來源`。`_TEMPLATE.md` 帶同一組
標題,測試一起掃,確保範本永遠跟規範同步。

## 5. 首個領域檔 `drivetrain-reduction.md` 內容大綱

- **適用情境**:要旋轉動力的減速/增矩,但沒指名機構型式。已指名者跳過選型、直接讀建模要點。
- **選型速查表**(一張表比較):欄位=構型 | 單級減速比 | 扭矩密度 | 背隙 | 剛性 | 效率 | 成本 |
  形態 | 典型應用。含 7 種構型 + 「直驅(無減速)」對照列。
- **7 種構型**,每種給「選型維度(典型範圍)」+「示意版建模要點(只用既有能力)」+「做不到的事」。
  下表為配方**初稿**——最終入庫版一律以 §7 第 0 層預驗結果為準(驗不過就改寫):

  | 構型 | 選型重點 | 示意建模方式(待預驗) | 明確做不到 |
  |---|---|---|---|
  | **行星** | 單級 3–10:1,同軸緊湊、高剛性、效率高 | 太陽/行星輪用 `gear()`;內齒環兩候選:benchmark 式**直接指定內齒三徑的梯形內齒**(有前例,首選)或環筒減放大背隙的 `gear()`(預驗擇一);行星架+銷。**指向 dogfood `models/planetary_reducer/`** | 三處嚙合相位同時對齊、公轉+自轉複合運動(靜態示意,不寫 MOTION) |
  | **諧波** | 50–160:1,背隙近零、輕,手腕/協作臂 | 剛輪=內齒環示意、柔輪=薄壁杯畫正圓留間隙、波發生器=橢圓凸輪 | 柔輪彈性變形、齒差嚙合(靜態示意) |
  | **擺線/RV** | 30–171:1,剛性抗衝擊最強,肩/基座大關節 | 擺線盤=epitrochoid 取樣點拉伸、偏心軸雙盤 180°、滾針圓柱陣列 | 偏心擺動運動(靜態偏心位姿) |
  | **蝸輪蝸桿** | 5–100:1,**自鎖**、效率低 | 蝸桿=螺旋掃掠梯形牙、蝸輪用直齒 `gear()` 代替(明講) | 真實包絡齒面、嚙合驗證 |
  | **正齒輪系** | 單級 1–6:1,**本 repo 甜蜜點** | 全用 `gear()`,閉式相位、有現成運動耦合契約(參考 steering_box_rack_pinion) | 無(能力範圍內) |
  | **同步帶** | 1–8:1,軸距自由(SCARA 前臂) | 帶輪=`gear()`、帶體=兩弧+公切線截面拉伸 | 帶張緊變形、齒形嚙合 |

  (傘齒/凸輪分度器列為「未涵蓋,未來領域檔」,示範擴充鉤子。)

- **機器手臂關節推薦表**:<10 Nm 手腕→諧波;10–100 Nm→諧波/行星;>100 Nm→RV 擺線;
  協作臂全身→諧波;低成本教育臂→行星/同步帶。
- **資料信心與來源**:全檔為教科書/型錄典型範圍〔信心:中〕,供構型比較用、非設計依據;
  最終數值仍走既有的「規格假設 → 使用者確認」閘。**選型速查表與關節推薦表逐列標信心**
  (不只檔尾一句),上線前人工過一遍數值。

### 5.1 行星 dogfood:`models/planetary_reducer/`

預驗產生器收斂成正式參考模型(靜態示意,不寫 MOTION——複合行星運動明列做不到):
太陽/行星/內齒環/行星架/銷,PARAMS 化(module、齒數組、厚度),`_check_params` 防呆
(齒數組必須滿足裝配條件 z_ring = z_sun + 2·z_planet 等),INTENDED_CONTACT 只列銷×行星輪
軸孔(嚙合留間隙、不進白名單),`check_geometry` 全綠。KB 行星節與 prompt 皆指向它。

## 6. prompt.mjs 整合(三個錨點,總增量約 8–10 行;KB 內容零進 prompt)

- **錨點 A**(`# 工作區`段,齒輪齒條指引之後):傳動/減速/致動機構「構型未定」的需求 →
  先 `Read apps/cad-chat/kb/INDEX.md` 找領域檔 → **把該領域檔整檔 Read**(turn 2 靠 resume
  拿建模要點,只讀片段下一回合就沒配方)→ 挑 2–3 候選 → 整合進**同一次** `emit_clarify` →
  使用者選定後照該構型建模要點做、誠實轉述「做不到的事」。
  **優先序消歧(必寫)**:已指名齒輪齒條/嚙合傳動 → 走既有 `steering_box_rack_pinion`
  硬編參考,不查 KB;**構型未定**的減速/傳動需求才查 KB。
  **負例防誤觸**:幾何已完全確定的單一零件(如 10mm 立方體、法蘭、支架)與已有硬編參考的
  需求(龍門/齒輪齒條)不查 KB。
- **錨點 B**(`emit_clarify` 工具契約句尾):傳動/減速構型未定時「構型選型」必列入澄清選項,
  label 寫「構型名——一行取捨摘要」、value 寫選定後可直接開工的完整配置。
- **錨點 C**(流程「0 理解」行,半句):提高觸發召回率。

**關鍵**:KB 內容**不進 prompt**,是 agent 需要時才 Read 進來的。prompt 只多約 8–10 行、
未來加再多領域也零增長。實作時注意錨點插入位置與近期新增的 prompt 段(鈑金等)互不打架。

## 7. 驗證計畫(三層)

- **第 0 層:配方預驗(交付期,一次性)**——§2 裁決 5 的執行面:七種構型的示意配方各寫
  一次性產生器(scratchpad 跑,不留檔;行星那支收斂成 `models/planetary_reducer/`),
  實跑 `check_geometry`(有效實體 + 干涉)全綠才入庫;驗不過當場改配方。這把「agent 現刻
  幾何燒 retry」的風險從執行期移到交付期,一次坐實。
- **L1 格式守護測試**(免 LLM,新增 `src/server/prompt.kb.test.js`)——**驗規範不驗內容**:
  prompt 引用的 KB 路徑存在、INDEX 列的檔都存在、kb/ 下的領域檔都被 INDEX 列到(雙向抓
  漂移)、每個領域檔含全部必要章節、範本也含同組章節。→ **使用者自行擴充寫壞格式時,
  測試會紅字直指缺哪個章節**,但不會綁死內容。
- **L4 真回合測試**(需真 LLM,gated 煙測 `smoke_kb_clarify_live.py`,**一條對話兩回合**,
  結構仿 `smoke_image_clarify_live.py`):
  - **turn 1**:丟「機器手臂關節用馬達減速機,40 Nm、減速比 50,構型請給建議」,斷言:
    出現澄清卡、選項含**≥2 種非正齒輪的真實構型**(諧波/行星/擺線/RV/蝸輪/同步帶)、
    **沒有搶跑去直接建模**。這是對「只會兩顆齒輪」病灶的直接反證。
  - **turn 2**:程式化點選**行星**選項(配方最成熟、有 dogfood 錨點),斷言:build 成功、
    走到 present(version/artifact 事件出現)。這是「做到底」的驗收線——選型漂亮但建不出來
    不算過。
  - 已知限制:Read 動作不進 SSE 事件流,無法直接斷言「KB 真的被讀過」,以「選項含多種真實
    構型+取捨措辭」為可觀測代理;守的是**行為契約**(先選型澄清、不搶跑、選定後建得出來),
    不是檢索本身。

## 8. 風險與邊界

- **工程數值可能寫錯**:KB 只給範圍不給假精度、逐列信心標註、最終數值仍走使用者確認閘;
  L4 不斷言任何數值;速查表與推薦表上線前人工過數值。
- **示意配方建不出來** → 已由第 0 層預驗承接(入庫的配方全數驗過);殘餘風險只剩 agent
  對驗過配方的走樣執行,由既有 retry/edits 迴圈 + L4 turn 2 把關。
- **誤觸發簡單需求**:靠「傳動機構 + 構型未定」雙條件 + 負例 + 硬編參考優先序讓位;真跑時
  觀察到誤觸發再收緊措辭。
- **教訓迴圈交互**:KB 構型建模若在真實使用中失敗,照常進教訓錄製/蒸餾(不特別排除)——
  預驗已把可預期的失敗清掉,殘餘的紅是真訊號,值得累積。
- **建模契約的坑**(KB 每個構型的建模要點都會提醒):齒對正確相位/留間隙**不要**列入干涉
  白名單;軸孔/銷/壓配**要**列入;運動耦合只用於真滾動幾何(正齒輪對/齒條),諧波/擺線/
  蝸輪**絕不**耦合;純靜態示意可不寫運動宣告。
